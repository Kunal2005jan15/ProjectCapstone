# ml-service — Sales Forecasting (build #1 of N)

Rebuilt from scratch after the last review. This folder follows the 12-step pipeline
the ML lead sent, with **one folder per stage** so the pipeline is traceable end to end —
in the code, in the repo, and in commit messages.

```
Data Collection → Data Cleaning → Preprocessing → Feature Engineering →
Train/Test Split → Model Training → Model Evaluation → Model Saving (.joblib) →
Load Model → Real-Time Data → Prediction → Send Prediction to Frontend
```

## Why this structure

- **Steps 1–4 (Collection, Cleaning, Preprocessing incl. normalization, Feature Engineering)
  live entirely inside `notebooks/01_eda_sales_forecasting.ipynb`**, not in separate module
  folders. This is deliberate while the data's still being explored — a `data_collection/`,
  `data_cleaning/`, `preprocessing/`, `feature_engineering/` folder next to the notebook, each
  half-duplicating what the notebook already does, is exactly the kind of thing that reads as
  messy in review. One working notebook beats four half-synced files.
- **Steps 5–12 (Split, Train, Evaluate, Save, Load, Predict, Serve) stay as real modules** under
  `modeling/` and `inference/`, because those need to be *called* — by a training script, by a
  FastAPI service — not just run top-to-bottom once in a notebook.
- **The hand-off between the two is a file, not shared memory:** the notebook writes
  `app/data/processed/sales_daily.csv`, and `modeling/train_test_split.py` reads it back in.
  Nothing in `modeling/` or `inference/` depends on notebook internals — run the notebook once,
  then the scripts work from the CSV it produced.
- Once the EDA/feature logic in the notebook stabilizes, promoting it into proper modules
  (mirroring `modeling/`'s pattern) is a reasonable next step — just not before the logic itself
  is settled.
- `app/data/raw/` is never modified by code — treat it as read-only input.
- `models_store/` holds trained `.joblib` files. Never commit trained models to git (see `.gitignore`) —
  they're regenerated by running the pipeline, and get large fast.

## Where to start: Sales Forecasting

We're building this model first (inventory alerts and recommendations come after, per the
proposal — they're rule-based, not ML, so they're much faster once forecasting is done).

**Primary dataset:** `restaurant_sales_data.csv` — 2 full years (2022–2023), item + category
level, one row per order line. This is the only dataset with enough history for Prophet to
learn weekly *and* yearly seasonality properly.

**Secondary/validation dataset:** the pizza dataset (`pizza/orders.csv` + `order_details.csv`)
— one full year (2015), used to sanity-check that the methodology generalizes across a second,
independently-collected dataset. This is exactly the "validated on real datasets" story from
the proposal (§6.2) and business research doc (§10).

`coffee/` (6 days) and `hotel_restaurant_orders.csv` (1 month) are too short a time span for
time-series forecasting — keep them for later (menu/catalog structure reference, or as extra
cold-start seeding examples), not for training.

### Pipeline order for this model

1. Run `01_eda_sales_forecasting.ipynb` top to bottom — it does Steps 1–4 (Collection,
   Cleaning, Preprocessing + normalization, Feature Engineering) and EDA, and writes
   `app/data/processed/sales_daily.csv` + `sales_daily_normalized.csv` at the end.
2. `modeling/train_model.py` reads that CSV, trains Prophet per item (or per category, if
   per-item is too sparse — the notebook's "days of history per item" section tells you which).
3. `modeling/evaluate_model.py` scores each trained model against its held-out test window.
4. `modeling/save_model.py` writes one `.joblib` per item/category to `models_store/`.
5. `inference/serve_api.py` is a FastAPI stub — this is what the Spring Boot backend will call
   to get predictions, once it exists. Not urgent this week.

Once the notebook's logic is stable (no more changes week to week), promoting Steps 1–4 into
proper `data_collection/` / `data_cleaning/` / `preprocessing/` / `feature_engineering/` modules
(same pattern as `modeling/`) is the natural next step — just not before then.

## Git workflow

Follow `docs/07-branching-workflow.md` from the shared docs repo. As ML lead, suggested
branch for this: `feature/ml-sales-forecasting-eda`, one commit per pipeline stage as the
notebook and modeling scripts fill in, e.g.:

```
feat(eda): steps 1-4 inline in EDA notebook — collection, cleaning, preprocessing, feature engineering
feat(modeling): train Prophet per item from processed sales_daily.csv
feat(modeling): evaluate + save trained models to models_store/
```

Small, stage-scoped commits make it obvious in review exactly which pipeline step changed —
this was part of what got flagged last time.
